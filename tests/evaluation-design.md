# Skill 评估设计规范

本规范用于设计 agent-led-swe 的行为评估，明确评估目标、判断标准、场景设置与证据要求。它不规定 Agent 必须采用的具体步骤或文件结构，也不代替单轮测试计划。

## 1. 评估目标

检验 Agent 能否借助 skill，根据任务要求和仓库现状，选择适当的开发活动与协作方式，形成符合目标、便于审阅和接续的成果。

分别回答三个问题：

- **是否适当地采用 skill**：理解任务和已有约定，选择必要活动，复用已有依据，处理实际冲突。
- **是否达到设计目标**：重要选择能够被审阅，实现有依据，反馈能落实，约定与实际状态可以接续。
- **是否产生实际价值**：人更容易理解和把关工作，遗漏与重复确认减少，记录有用且负担适当。

读取指导、生成文件是执行证据，不是评估目的。功能正确性由独立 verifier 判断，不能替代对工作组织与协作的分析。

## 2. 适用要求与冲突判断

先明确用户目标、仓库约定和被测 skill 各自要求什么，再确定当前场景的预期行为。

| 情况 | 预期行为 |
| --- | --- |
| 已有规范或成果足以满足需要 | 直接复用，不再建立重复规则或记录。 |
| 已有依据只覆盖部分需要 | 在项目已有组织方式中补足必要信息。 |
| skill 提供通用做法或模板 | 根据任务规模与仓库习惯裁剪，不将模板视为强制产物。 |
| 要求确实无法同时满足 | 识别具体冲突、范围与影响，依据用户授权处理；重要未决取舍交由用户判断。 |

区分硬冲突、职责不同和适配说明不足。使用说明在实现后完成，不代表缺少设计；没有独立设计文件，也不代表没有设计依据。应核查相关信息的实际内容、位置与形成时机。

用户明确要求优先于 skill 的通用做法。skill 不自动取得修改仓库规范或扩大任务范围的权限；仓库未明确要求某项记录，也不代表实现用户目标时不需要它。

## 3. 共同评估标准

| 维度 | 要回答的问题 | 主要证据 |
| --- | --- | --- |
| 理解与适配 | 是否理解任务范围、已有成果与规范，并据此判断需要补什么？ | 仓库调查、采用的依据、实际工作范围。 |
| 工作组织 | 必要活动是否衔接合理，是否有依据不足就实施或无必要的重复工作？ | 行动顺序、关键产出及其形成时机。 |
| 人机协作 | 重要选择是否得到适当把关，已授权事项是否自主推进，反馈与已有决定是否得到落实？ | 问答、决策材料及后续修改。 |
| 记录与文档 | 必要信息是否准确、易读、容易找到，足以支持当前审阅和后续接续？ | 已有记录的复用、新增内容、更新时机与一致性。 |
| 验证与交付 | 是否实际检查承诺的行为，如实说明结果、限制与剩余问题？ | 测试和审阅证据、交付说明、独立 verifier 结果。 |
| 过程负担 | 是否出现无必要的审批、重复文档、无关设计或反复确认？ | 完整交互与操作轨迹，结合任务需要判断。 |

“必要”由当前场景确定。不同场景不期待相同的步骤和产物，也不按文件数量、指导读取次数或统一篇幅判断成功。

## 4. 场景设置

场景从两个方面描述：**仓库已有状态**与**用户任务及协作要求**。首批选择以下代表性组合，不要求穷举所有组合。

| 场景 | 条件 | 预期表现 | 重点识别的问题 |
| --- | --- | --- | --- |
| A：成熟仓库中的功能开发 | 有明确规范与结构；用户要求完成功能，没有额外指定协作流程。 | 沿用工程方式，补充当前变更所需的设计、测试与说明；记录详略与任务相称。 | 强加完整文档体系、忽略既有规范、遗漏必要依据。 |
| B：成熟仓库中的持续协作开发 | 仓库条件与 A 相近；用户明确需要审阅重要设计，并能接续工作。 | 在相关实现展开前提供重要选择的审阅依据；保存确认的约定，维护进展、实际验证与未决事项。 | 约定仅留在对话、依赖用户逐步提醒、用使用说明替代全部工作记录。 |
| C：缺少规范的新项目 | 初始代码与规范较少；用户提供大致目标并授权推进。 | 澄清影响方向的需求，形成适量工程约定与设计，再实现和验证。 | 凭猜测直接编码，或过度设计而无法推进实现。 |
| D：已有成果的接续修改 | 已有需求、设计、代码与部分记录；用户提出后续修改。 | 核对实际状态，复用有效成果，识别影响，更新相关记录并验证。 | 无视旧约定重新开始、盲信过时记录、修改后文档与代码脱节。 |

A、B 可以复用同一真实功能任务，分别观察默认适配能力与明确协作需求下的执行能力。仓库状态、任务规模和其他条件尽量保持一致，并记录仍存在的差异。

以上是场景设计，不表示已经接入或验证。先明确具体输入和预期，再选择真实任务；历史 cattrs 运行保留原有请求与定义，不事后重命名为新场景。

## 5. 任务与交互设计

每个场景在运行前明确：用户要什么结果、哪些选择已授权；仓库已有何种规范与成果；必须满足哪些效果，以及哪些额外负担没有必要。

任务请求表达用户需要的结果，不替 Agent 安排 skill 的执行步骤。例如，需要持续协作时可以明确“重要设计可供审阅，约定和进展能够接续”，但不因此指定必须读取的指导、模板、文件名或固定阶段。项目本身已有的明确要求仍应保留。

模拟用户依据任务、权限、已有对话与当前成果自主回应，不负责提醒开发 Agent 完成 skill 流程。固定任务与用户设定，允许实际对话自然分化；不得为得到预期轨迹而改写回复、安排返工或选择性重试。具体接入与边界见 [模拟用户协议](protocol.md#agent-based-模拟用户)。

## 6. 证据与结论

分析使用完整轨迹、项目产物及其变化，区分观察事实、归因假设和未验证内容。按维度说明符合、部分符合或不符合的具体要求；未覆盖或证据不足时如实标明，不合成总分，也不将这些定性结论并入功能成绩。

例如：实现前已在对话中澄清接口，但项目中找不到确认后的约定。对于要求持续接续的场景 B，这是信息保存缺口；不能仅凭没有名为 `design.md` 的文件作出同样判断。

区分规范缺失、表述不清、适用冲突与明确要求未执行。读取指导不证明落实，最终产物不证明其事前已经形成，评测框架保存的轨迹也不等于 Agent 完成了项目记录。

模拟用户错误、环境限制、模型波动及需求与 verifier 的歧义单独分析。用户接受不代替功能正确；运行核查有效也不保证每次用户反馈正确。不同组回复或回合数不同，本身不构成失败。

当前／候选版本对照用于判断修改效果；要证明 skill 相比不用 skill 的收益，需要无 skill 对照。单个任务、单次运行只支持有限观察；用于分析和调优的任务明确标为开发集。

修改请求或场景后创建新的冻结记录，保留历史结果；未变化的执行约定直接引用，不在各轮重复定义。
