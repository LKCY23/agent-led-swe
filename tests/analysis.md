# 测试历史分析

分析在测试之后进行，由人类与 Agent 按需审阅；不由测试程序自动调用模型，不修改 verifier 成绩或已有轨迹。

评估维度与场景预期遵循 [评估设计规范](evaluation-design.md)。先核对该轮已冻结的要求，再分析证据，不事后添加判据。

## 读取依据

先确认运行目录的 plan、任务来源、skill 版本／哈希、Agent 与模型配置、预算和组别。核对原生安装／调用、环境审计和执行状态，再读取 verifier 结果。旧的 document-reading 模式不能与 native 模式混为同一对照。

使用完整轨迹、工具实际结果、前后文件及变化清单检查过程；不要只根据最终回复或某个文件名推断是否完成工作。测试失败、未运行、环境错误和证据不足分开解释。

## 要回答的问题

- 测试机制是否按配置运行，隔离、skill 调用、采集与 verifier 是否正常？
- Agent 是否理解并保留要求，准备依据、推进和处理反馈的方式是否合理？
- 模拟用户的回答是否有任务、权限或成果证据支持，是否区分已有要求与新决定？两组回答可以自然不同；依据具体证据分析越权、事实错误、约定遗忘等问题，不以措辞或轮次是否一致判定有效性。
- 文档和交付说明是否准确、适量、能支持审阅与接续？
- 哪些观察可能由 skill 引起，哪些也可能来自模型波动、任务、预算或环境？
- 下一轮值得验证什么变化，怎样避免只针对已经看过的用例调优？

## 保存分析

新建独立的分析记录，引用原运行目录与具体证据位置。每个发现区分：**观察事实 → 支撑证据 → 归因假设与反证 → 优化建议或待确认事项**。

不输出工程／文档的硬性 pass/fail，不把分析意见并入任务分数。即使 verifier 通过，也可以记录流程缺陷；即使 verifier 未通过，也不能无依据归因于 skill。旧的 LLM judge 判分保留为历史材料，不作为新的成绩来源。
