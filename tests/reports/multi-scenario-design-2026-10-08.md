# 多场景评测：任务选择与用户目标

2026-10-08。依据 [评估设计规范](../evaluation-design.md)提出四个场景：A 使用 TOMLKit 功能题；B 经独立筛选推荐 ofetch 熔断器；C 使用从空工作目录构建 gRPC 服务的任务；D 使用真实运行留下的 cattrs 成果做接续修复。

本轮完成来源、起始状态、需求和验收代码的静态核查，未接入新执行器、构建环境或调用模型。以下请求是待采用的场景定义，不替换历史请求，也不代表任务已经获得运行资格。

## 1. 组合与选择理由

| 场景 | 选定 case | 起始状态 | 用户目标 | 要观察的适配 |
| --- | --- | --- | --- | --- |
| A：成熟仓库功能开发 | TOMLKit table converters | 原始仓库，有代码、测试、文档、工具配置和 CI | 完成转换能力及必要测试和说明 | 沿用已有规范，适量补充依据，避免额外流程负担。 |
| B：成熟仓库持续协作 | ofetch per-origin circuit breaker | 已有 TypeScript 请求管线、hooks、重试、测试和工具规范 | 交付熔断能力，并支持重要设计审阅与后续接续 | 能否组织相互关联的机制、保留约定并形成可接续成果。 |
| C：缺少规范的新项目 | Terminal-Bench 2 的 kv-store-grpc | Python 环境与空 `/app`，没有应用源码或项目规范 | 交付可运行、可继续修改的小型 gRPC 服务 | 能否建立适量组织与运行说明，而不是直接交付零散脚本或过度搭建。 |
| D：已有成果接续修复 | cattrs 真实候选产物中的两处行为修复 | 已有实现、自测、使用说明和变更记录 | 修正指定行为，保留已有能力并同步记录 | 能否核实旧成果、识别过时约定、局部修复并验证，而非重做整个功能。 |

各场景分别按其目标评价；A/B 使用不同任务，不能将差异单独归因于协作要求。D 来自已分析的开发集成果，C 只覆盖轻量新项目。通过这一组也不能宣称已经验证大型新项目或多个 Process 的协调。

## 2. A：TOMLKit 表结构转换

### 来源与起始状态

- 来源：SWE-Interact 的 DeepSWE 子集，`deepswe_tomlkit-toml-table-converters`，固定版本 `b32f98c3b8f76ca65e84341d1f30e5af7135f85d`。
- 项目：`python-poetry/tomlkit`，代码基点 `dd05eebc8ed9e30fc6c223088a5a450cb54c1cab`。
- 已核查 README、`pyproject.toml`、pre-commit 配置、CI 与文档入口：已有 Poetry、pytest、Ruff、Sphinx 及多版本 CI 约定。完整源码和适用规范应原样保留，不注入 skill 模板。
- [原始功能要求](https://github.com/scaleapi/SWE-Interact/blob/b32f98c3b8f76ca65e84341d1f30e5af7135f85d/data/singleturn/deepswe_tomlkit-toml-table-converters/instruction.md)、[仓库配置](https://github.com/python-poetry/tomlkit/blob/dd05eebc8ed9e30fc6c223088a5a450cb54c1cab/pyproject.toml)、[CI](https://github.com/python-poetry/tomlkit/blob/dd05eebc8ed9e30fc6c223088a5a450cb54c1cab/.github/workflows/tests.yml)。

### A：给开发 Agent 的请求

> 请给 TOMLKit 增加普通表、内联表和点号键表示之间的转换能力，方便调用方调整 TOML 的结构表示。转换应保持数据含义，并按约定迁移注释，转换后的文档仍能正确序列化和解析。
>
> 请完成功能、必要测试和使用说明，沿用仓库已有的结构与工程规范。我有确定的公开接口和边界行为要求，你可以向我确认。实现已授权，约定范围内的内部设计、文件安排和测试方式由你决定；需要改变功能目标或已有兼容承诺时，先说明影响。完成后说明实际结果、验证情况与限制。

不额外要求持续协作记录，也不禁止必要设计或记录。评估其默认适配是否合理，不把 B 的专门协作要求追加为 A 的判据。

### 模拟用户掌握的完整目标

提供原始功能要求：四个转换函数的名称与导出位置、原地修改并返回同一文档、round-trip、`ConversionError.key_path`、错误路径处理、递归转换、AoT 限制、`max_depth` 和注释迁移规则。不得由用户临时补造这些接口语义。

用户可以澄清目标、审阅方案并接受不违反约束的取舍；内部实现选择交由开发 Agent。用户不接触隐藏测试或参考补丁，不规定文件数、模板或 skill 执行步骤。

### 验收与场景证据

[原验收补丁](https://github.com/scaleapi/SWE-Interact/blob/b32f98c3b8f76ca65e84341d1f30e5af7135f85d/data/singleturn/deepswe_tomlkit-toml-table-converters/tests/test.patch)新增 60 个测试函数，覆盖转换、路径、注释、返回对象及 round-trip；这是静态数量，不是已运行计数。保留原 `base` / `new` 断言，移除原 benchmark 的外部五阶段调度。

原 `base` 排除 `tests/toml-test`、formatter、merge 及新增 convert 测试，不能报告为完整仓库回归。README 要求的 toml-test 子模块和项目工具应在环境准备时固定；额外仓库检查与 canonical verifier 分开报告。测试名涉及注释不保证每项注释承诺都被充分验证，例如 `test_comments_collected` 仅断言值未改变；语义覆盖仍须审阅。

A 观察是否适量采用已有工程方式，不以是否出现 `plan.md` 或 `design.md` 判断成功。

## 3. B：ofetch 熔断器与持续协作

选题、初始请求、完整需求来源和资格检查要求统一保存在 [B 场景选题说明](scenario-b-selection-2026-10-08.md)。四题比较后推荐 ofetch，HTTPX 和 Awilix 等保留为备选，不同时接入。

用户目标是在现有请求管线中增加按 origin 隔离的熔断与恢复探测，同时使重要机制设计可审阅、约定和实际验证结果可接续。原题的状态、重试、失败计算和共享语义保持不变；具体交互由模拟用户自主完成，不保证发生返工或指定轮次。

## 4. C：从零构建小型 gRPC KV 服务

### 来源与起始状态

- 来源：Terminal-Bench 2，`kv-store-grpc`，固定版本 `2fd12b88aafdd04a52c298e3940bcb189f9766d6`。
- [原始任务](https://github.com/harbor-framework/terminal-bench-2/blob/2fd12b88aafdd04a52c298e3940bcb189f9766d6/kv-store-grpc/instruction.md)、[环境](https://github.com/harbor-framework/terminal-bench-2/blob/2fd12b88aafdd04a52c298e3940bcb189f9766d6/kv-store-grpc/environment/Dockerfile)、[验收代码](https://github.com/harbor-framework/terminal-bench-2/blob/2fd12b88aafdd04a52c298e3940bcb189f9766d6/kv-store-grpc/tests/test_outputs.py)。
- 原 Dockerfile 只有 Python 3.13 基础镜像与 `/app` 工作目录，没有应用源码、模板或项目规范，符合轻量新项目的起始条件。任务有明确 gRPC 兼容接口，因此它测试组织与细化能力，不测试任意选择架构或技术栈的能力。

### 给开发 Agent 的请求

> 我需要一个供其他程序调用的小型 Python gRPC 键值服务，保存字符串键对应的整数，支持写入、读取和覆盖更新。数据放在进程内存中即可。目前工作目录没有应用代码，我有调用方需要遵循的协议和运行要求，你可以向我确认。
>
> 请交付可运行的服务、必要的验证和简短的构建与启动说明，让后续维护者能从这些材料继续修改。实现已授权，按这个小服务的规模组织代码和工程约定；影响调用方的未定选择请说明，其余内部选择自行决定。

### 模拟用户掌握的完整目标

提供原任务完整要求：Python dict 存储；`grpcio` / `grpcio-tools` 1.73.0；`KVStore` 服务；`GetValRequest.key`、`SetValRequest.key/value` 与响应 `val`；规定的 proto、生成文件、`server.py` 和 `Server` 类；端口 5328；交付时保持服务运行。

这些路径、名称和版本属于外部接入要求，不是为推动 skill 而添加的流程规则。未定义的行为，例如读取不存在的键，交由 Agent 提出合理处理并说明，不编造隐藏判据。不增加持久化、认证、分布式部署等目标。

构建与使用说明、后续可修改性是本场景增加的用户目标，需在结果中注明为适配任务，而非原榜单成绩。

### 验收与接入条件

原 verifier 有 7 个测试函数，检查文件、生成绑定、类、端口、gRPC 通信及设置／读取／更新。没有覆盖不存在的键、持久化或完整并发语义，不据此宣称这些能力通过。

该任务验收运行中的服务，不能直接套用 cattrs 的纯文件验收。接入时应记录 worker 停止前的端口与协议可用性证据，再从最终产物在独立环境启动规定入口并运行原测试；生命周期证据与功能验收分开。若不能保留这些语义，该任务不得进入正式运行。

依赖需离线准备，并记录将原任务联网安装迁移到环境准备阶段的差异。原测试本身会安装测试依赖，适配时固定依赖而不改变断言。其握手测试允许 `grpc.RpcError`，需结合后续真实读写测试解释结果，不能仅凭端口或握手判定功能正确。

观察重点是最低限度的代码组织、协议与运行说明、实际检查及适量取舍。无需完整工程文档体系，不能将这一小型服务当作大型项目的代理。

## 5. D：接续 cattrs 的真实待修复成果

### 来源与起始状态

使用 `cattrs-user-revision-20261008/candidate/after` 的最终项目快照。它有实际运行生成的实现、自测、使用说明、README 与 HISTORY 变更；原独立验收为基础 7/7、新功能 67/69。详见 [原运行报告](cattrs-user-revision-2026-10-08.md)。

这是来自真实轨迹的派生修复场景，不是新的公开 benchmark 题，也不是独立未见集。两种 skill 均从同一快照启动新会话，不各自沿用自己的上一轮成果。

保留源码、自测和文档，尤其保留与新要求不一致的 TypedDict 说明，供 Agent 自行发现并同步。只清理声明的缓存或运行垃圾，不补造事前设计、决定日志和计划；不把隐藏测试、参考答案、成绩或完整旧聊天放进 solver 工作区。

### 给开发 Agent 的请求

> 这份代码已经实现了 partial structuring，但还有两处行为需要修正：TypedDict 的必需字段转换失败时，结果的 value 应为 None；在 detailed_validation=True 时，即使失败字段使用默认值后仍能构造对象，errors 也应保留这次字段失败的信息。
>
> 请从当前实现继续处理，保留其他已实现行为，检查相关测试与说明是否需要更新，并验证修改及回归情况。希望改动集中在这次修复涉及的部分；内部实现与文件安排由你决定，完成后说明修复依据、结果和剩余限制。

第二条将此前需求与验收间不够明确的边界明确为本轮要求，不能伪装成用户早已无歧义地表达过的承诺。其余原始功能要求仍提供给模拟用户；它不能沿用上轮错误接受结论来否定本轮目标。

### 验收与场景证据

复用 cattrs 的基础 7 项和新增 69 项 canonical 测试，关注两个原失败断言及其他行为的回归，不只运行两个定向检查。原快照的失败已有证据，但制作新公开输入后仍需重做预检，核对处理没有改变任务。

重点观察是否先核查现状，复用已有实现、发现并修正文档冲突；是否保留未受影响的约定，给出实际回归结果。允许简短修复说明，不要求重建整个 Process 的历史或重新进行全部设计审批。

## 6. 用户设定与对照方式

复用自主模拟用户的通用规则，但不能把现有 cattrs 专属权限直接复制给其他任务。接入时按场景提供角色、固定目标、偏好、授权和已有材料；各场景的两个 skill 版本使用相同目标，B 明确包含持续协作需要。

两版本使用相同任务输入、用户设定、模型、工具与预算，新建独立会话和工作区。用户根据上下文自主回答，允许不同反馈；不因回复不符合预想而改写、过滤或重试。

保留当前／候选 skill 版本对照，不同时扩展到多种 Agent 或模型。四场景各一对意味着最多八次开发运行，但本设计不自动启动它们。先取得任务资格，再按本轮明确的执行范围冻结预算与矩阵；不直接沿用上游超时，也不在看到结果后延长失败组预算。

## 7. 接入顺序与当前边界

1. **TOMLKit A / ofetch B**：分别固定源码、依赖和 verifier，完成起始失败／参考通过与项目回归预检；分别冻结任务请求。每题内部比较 skill 版本，不将两题直接作为用户要求的控制变量实验。
2. **cattrs D**：从已记录快照制作独立输入，保留真实已有成果，复查起始失败与修复后的验收能力。
3. **gRPC C**：准备离线环境，验证构建、运行状态保存、停止与独立启动验收的完整链路，再进入模型试跑。

现有 `run_collaboration.py` 仍固定 cattrs 输入与场景目录，尚不能直接运行 A/B/C 或 D 的自定义起点。后续实现应让它选择任务输入、用户设定和 verifier，复用现有原生用户、隔离与采集机制；不重新实现一套模拟用户。

本轮未修改 skill、当前任务请求或执行器。暂不选用另外核查的财务文档处理、日志汇总任务，因为它们主要验收一次性数据产物；异步取消任务只要求单个函数，难以充分观察新项目组织。无需为凑数量全部接入。
