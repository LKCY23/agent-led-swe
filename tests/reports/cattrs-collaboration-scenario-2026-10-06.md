# cattrs 协作评测场景草案

状态：待审阅，未接入、预检或运行。本文细化一项稳定需求下的协作场景，替代[前次调研](swe-interact-research-2026-10-06.md)中沿用固定五步的接入建议。实现仍以审定后的方案为依据。

## 1. 要检验什么

使用 cattrs 的真实功能题，观察 Agent 能否自行组织需求澄清、必要设计、实现、验证和交付，并通过文件与用户保持一致。重点是：

1. 必要的设计和约定是否先于依赖它们的实现，实际结果是否在执行后记录。
2. 用户能否把关重要问题，同时不必不断提醒 Agent 推进流程。
3. 文档是否具体、精炼、便于审阅，并与实际代码和验证状态一致。

这是一项 Process 的开发用例，不覆盖多 Process 的 Workflow、真实需求变更、长期维护或跨会话恢复。原生显式调用只能检验调用后的执行，不能证明 skill 会被自然选中。单次配对用于发现问题，不支持统计优越性结论。

## 3. 给 Agent 的初始请求

以下正文两组完全相同。skill 组只在开头增加对应宿主的原生调用。

> 我想给 cattrs 增加部分转换和恢复能力：输入有些字段无效时，尽量保留有效结果，并允许补充数据后修复失败部分，而不是整次转换只能失败。
>
> 请新增 `partial_structure` 和 `PartialResult.refine`，支持 attrs 类、dataclass 和 TypedDict，同时保持现有转换行为兼容。我对公开接口和失败处理有一些具体要求，你可以向我确认。
>
> 请把功能实现、必要测试及使用说明一起完成。沿用仓库现有结构和规范，不引入新的运行时依赖。关键接口行为和重要取舍要让我能审阅，相关说明保存在项目中，简短、具体即可。
>
> 这项工作的实现已授权。约定范围内的内部设计、文件安排和测试方式由你决定；如果必须改变目标、兼容性承诺或引入新依赖，请先说明原因与建议。完成后说明实际实现和验证情况，以及尚未解决的问题。

它明确交付需要与授权，不规定先做什么、写几个文件或何时提交。初始输入不包含“必须先写计划”等流程提示；两组均有合理的文档交付要求，比较的是如何完成这些要求，而非是否猜到用户想要文档。

公共工作区保留原仓库说明、配置和既有文档，不注入 skill 模板。模拟用户资料、观察清单、参考补丁和隐藏测试均不放入公共工作区。

## 4. 模拟用户掌握的需求和偏好

### 功能要求

以下是原始任务的固定要求，不是临时增加的反馈。模拟用户可据此回答和审阅，不接触参考实现或隐藏测试。

| 主题 | 用户的确定要求 |
| --- | --- |
| 入口与结果 | `BaseConverter` 和顶层提供 `partial_structure`，导出 `PartialResult`；结果含 `value`（部分对象或 `None`）、`is_complete`、`structured_fields`（成功从输入转换的字段名 frozenset）、`failed_fields`（frozenset）、`errors`（异常或 `None`）与 `error_map`（字段名到异常）。 |
| 缺失与默认值 | 输入缺失的字段算失败，不算成功；失败字段有默认值时回退到默认值；必填字段无默认值时，`value` 为 `None`。 |
| 嵌套与集合 | 嵌套 attrs／dataclass 递归部分转换；子对象不完整但能产生值时保留部分值，父字段仍算失败；不能产生值则按普通字段失败处理。List／Dict 字段整体转换，任一元素失败则整个字段失败。 |
| 修复 | `refine(data)` 返回新的 `PartialResult`，用新输入修复失败字段，保留已经成功的字段。 |
| 特殊字段与验证 | `init=False` 字段不计入成功或失败集合；`forbid_extra_keys` 下额外键使结果不完整，但仍产生值；遵守 `detailed_validation`。 |
| 支持范围 | attrs 类、dataclass、TypedDict；保留既有转换行为。 |

对未规定的实现细节，模拟用户明确交由 Agent 根据仓库判断。若发现原需求和可信测试存在冲突，先记录任务有效性问题，不让模拟用户根据测试答案临时补充要求。

### 本场景增加的工程偏好

这些偏好已在初始请求中公开，不作为隐藏验收要求：沿用既有结构与规范、不新增运行时依赖、公共接口及重要取舍可审阅、说明简短并保存在项目中。不同合理实现均可接受，不要求复刻参考代码。

模拟用户不规定具体文档路径、模板、架构风格或必须由人批准每一步。已有授权与决定持续有效，普通技术选择不需要重复审批。若确实需要超出约定的取舍，模拟用户只依据固定目标和提供的证据回应；不能通过同意删除某项原始要求来让任务变容易。

## 5. 用户怎样回应，工作怎样继续

| 发生什么 | 模拟用户／运行环境怎样处理 |
| --- | --- |
| Agent 询问需求或边界 | 直接回答所问内容及影响该决定的相关约束；询问完整要求时提供完整要求。允许一次回答多个相关问题，不故意逐条拖延。 |
| Agent 提交接口或设计供审阅 | 对照固定需求，指出当前材料中可见的关键遗漏或矛盾，给出具体意见；内容充分时明确接受。不能先批准明知错误的方案，再故意要求返工。 |
| Agent 询问已委托的内部选择 | 明确沿用授权，由 Agent 判断；不凭个人臆测增加架构或实现要求。 |
| Agent 通过交互工具请求决定 | 回应具体问题。工具故障标为环境故障，不伪装成用户反对或要求重做。 |
| Agent 结束一轮并提交成果或声称完成 | 将回复送给同一模拟用户；用户可查看当前文档、未提交修改与已有提交，再回应。若有遗漏，集中反馈当前可辨认的问题，不要求先 commit 才能审阅。 |
| 用户有明确反馈 | 用同一原生会话继续工作，保留工作区。首轮不把每次回复重开会话，也不要求 Agent 回到预设阶段。 |
| 用户确认本次交付可接受 | 结束交互并冻结产物，独立运行 verifier；用户接受不等于功能通过。 |
| 到达预算或发生不可恢复故障 | 停止并保存部分成果及原因；不能当作完成，也不自动追加重试。 |

运行环境只负责传递问答、维持状态、控制预算和记录历史，不安排“现在写设计／现在实现／现在补测试”。不向用户模拟器提供 skill、观察清单或 baseline／skill 组别。

如果 Agent 尚未主动确认某些要求便提交实现，用户可在审阅时指出差异。分析时记录该要求何时实际传达，不能把未告知的精确接口名称或行为一律算作“遗漏已知要求”。在接受交付前，用户须核对全部固定要求；必要时说明尚未传达的要求，让 Agent 有机会处理。区分需求澄清不足、已知要求遗漏与模拟用户未正确回应。

模拟用户不能检查隐藏 verifier，也不能指导具体代码修复。它是否遵守固定需求和回应规则也要在事后核查；发生实质性违背时，保留运行证据并标明对比较有效性的影响。

## 6. 保留什么证据，怎样分析

测试程序保存双方消息、工具执行及退出状态、重要时点的文件快照和 diff、当前工作区与最终产物、原生 skill 加载证据、用量和停止原因。快照至少覆盖用户审阅、决定、测试及交付；结合文件写入事件核查先后，不能只靠最终文件或 mtime 推断。

功能由独立验收副本运行原题可信 `base`／`new` 测试。保留 Agent 自己编写的测试作为交付证据，可信测试恢复与覆盖只发生在验收副本。原五步 wrapper 的提交形状要求不作为功能门槛。起始代码应无法通过新增能力测试，参考实现应通过；未确认这些前，不开始模型试跑。原 `base` 测试仅覆盖 `test_errors.py`，报告须注明回归范围有限。

流程与文档由后续人工／Agent 结合历史分析，不新增自动 LLM judge 或综合分数：

| 观察点 | 判断依据 |
| --- | --- |
| 实现依据 | 对相关生产代码作出实质修改前，关键接口、失败处理、代码归属和验证安排是否已明确并有适当记录；允许先读代码、跑现有测试和必要的可行性试验。 |
| 决定与授权 | 未决重要取舍是否有问题、依据、建议与影响；已授权事项是否自主推进；没有真实决策事项时，不因没有审批而扣分。 |
| 反馈落实 | 用户已表达的要求是否进入有效约定，并落实到实现与验证；原有决定和有效成果是否被保留。 |
| 流程摩擦 | 是否重复询问、等待不必要审批、无故重建文档，或需要用户反复提醒同一事项；正常澄清和必要返工不自动算摩擦。 |
| 文档用途与可读性 | 人能否快速查明当前接口、关键理由、实现状态与未决项；说明是否具体、精炼、无矛盾、能定位依据；不按文件数量或固定字数判断。 |
| 结果与交付 | 测试结果是否在实际执行后记录，计划与结果是否区分，结论是否对应检查过的版本，未验证或受阻事项是否如实说明。 |

单独说明每项观察满足、存在问题、证据不足或本次未发生，并链接证据。模拟用户接受文档不等于文档质量已验证；人类可读性仍需实际审阅代表性产物。

## 7. 审定后如何推进

1. 先确认本场景的初始请求、用户规则及观察依据；本草案不授权运行。
2. 预检 cattrs 的环境、原始需求与可信测试一致性，再明确需要复用／修改的执行器能力：双向交互、原生会话继续、用户只读检查和完整证据采集。Harbor 可复用能力需据此选择，不预先承诺采用其五步调度。
3. 用模拟响应检查交互与隔离，包含主动提问、结束一轮后的用户反馈、重复授权及服务失败；确认两种 Agent 的支持边界。
4. 冻结首轮一种 Agent、solver 与用户模型及预算，开展 baseline／skill 各一次，再一起审阅轨迹与文档。

本轮模型调用预算为 0。后续试跑前须确定每组总时长、模型用量／费用上限、用户交互上限和故障处理，当前不提供可直接执行的运行配置。动态对话两组不必字句相同，但必须遵循相同需求、授权和回应规则；保留差异，不将一次配对结果单独归因于 skill。
