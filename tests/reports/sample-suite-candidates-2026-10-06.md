# agent-led-swe 样例组合建议

更新：用户已确认保留原四题，接入与预检已完成，见 [结果](four-task-integration-results-2026-10-06.md)。下文保留选题时的理由和风险；接续变体尚未执行。

建议采用 **4 个真实开发主任务 + 2 个接续变体**。首批准备 smolagents 与 xarray，第二批再接 NodeBB 与 Navidrome。这些是待审阅、待环境预检的候选，不是已经可以稳定运行的任务集。本轮没有修改执行入口、实现适配器、拉取任务镜像或启动 Agent 试跑。

选择依据是能否观察需求、设计、实现、验证和交付的衔接，而不是单看代码量、难度或 benchmark 名称。固定接口并不排除设计工作，但这组主要检验已有项目中的扩展、迁移与职责调整，不能据此宣称覆盖从零架构设计和全部人机协作能力。

## 1. 四个主任务

| 编号 | 真实任务 | 组合中的作用 | 优先级 |
| --- | --- | --- | --- |
| A | smolagents #1442：代码块改用 XML，并贯通可选自定义指令 | 跨组件迁移、需求覆盖、代码与文档同步 | 首批 |
| B | xarray #8840：将 Grouper／Resampler 开放为公共 API | API 扩展、内部边界调整、向后兼容与范围控制 | 首批 |
| C | NodeBB：集中管理邮件验证状态 | 共享状态职责收敛、多条业务路径集成与回归 | 第二批 |
| D | Navidrome：增加数据库备份与恢复 | 完整功能的配置、CLI、数据库和文件管理协作 | 第二批，有额外资格条件 |

### A. smolagents：跨组件格式迁移

- **身份与来源：** `huggingface__smolagents-1442`，采用作者仓库 FeatBench v1 数据；[原始 PR](https://github.com/huggingface/smolagents/pull/1442)。
- **工作内容：** 将代码提取、各类 Agent 的 prompt、规划结束标记、浏览器示例与用户文档同步改为 XML 约定，并支持可选的自定义指令。不能只改 parser 后就宣称迁移完成。
- **为什么适合：** 一般目标需要被展开为多处相互关联的修改；遗漏 prompt、错误提示、示例或文档，可能不直接体现为核心功能失败。可以观察 Agent 是否先说明迁移范围与依赖，再保持实现和交付说明一致。
- **已有验收：** 数据提供 7 个 F2P、321 个 P2P 选择器；涉及 `test_agents.py`、`test_gradio_ui.py`、`test_monitoring.py`、`test_utils.py`。这是声明的选择器数，不是本机已运行的测试数。
- **文档观察：** 文档更新是原需求的一部分，不是为测试 skill 附加的文件数量要求。重点看说明、示例和实际解析行为是否一致。
- **接入风险：** 需核查回归是否依赖模型下载或外部服务。原 PR 中“若干模型未出现性能下降”是作者的历史观察，不能将单元测试通过包装成我们重新验证了这些模型表现。

### B. xarray：公共 API 与兼容性演进

- **身份与来源：** `pydata__xarray-8840`，采用作者仓库 FeatBench v1 数据；[原始 PR](https://github.com/pydata/xarray/pull/8840)。
- **工作内容：** 开放 `UniqueGrouper`、`BinGrouper`、`TimeResampler`，让 Dataset／DataArray 的分组和重采样路径接受相应对象，保留已有调用方式，并更新 API 索引、用户指南和发布说明。
- **为什么适合：** 修改同时涉及公共入口、公共参数语义和内部实现；适合观察模块边界、兼容策略、设计理由与回归范围是否说清楚。多变量分组属于后续方向，不能借机扩大本次范围。
- **已有验收：** 数据提供 5 个 F2P、2,753 个 P2P 选择器；新增／修改的功能测试位于 `xarray/tests/test_groupby.py`，包括传统调用与 Grouper 对象的参数化覆盖。
- **文档观察：** 原需求明确包含 API 文档、示例、用户可见变更记录。查看这些材料是否能解释新旧用法及边界，而不是只检查文件是否存在。
- **接入风险：** 固定 pandas、NumPy、SciPy 等依赖和可选后端；核查完整指定回归的资源与离线要求。不能只跑新增 groupby 测试就声称全部兼容性已确认。

### C. NodeBB：邮件验证状态的职责收敛

- **身份与来源：** SWE-bench Pro V2，`instance_NodeBB__NodeBB-087e6020e490b4a1759f38c1ad03869511928263-vf2cf3cbd463b7ad942381f1c6d077626485a1e9e`；[任务与原生 verifier](https://github.com/scaleapi/SWE-bench_Pro-os/tree/main/v2/tasks/instance_NodeBB__NodeBB-087e6020e490b4a1759f38c1ad03869511928263-vf2cf3cbd463b7ad942381f1c6d077626485a1e9e)。
- **工作内容：** 提供集中查询和清理待验证邮件状态的方法，贯通邮件发送、资料更新、密码重置、确认和页面 header；正确处理邮箱大小写及重新发送时的旧状态。
- **为什么适合：** 核心不是多加两个函数，而是让调用方都遵循一致的状态规则。可以检验 Agent 是否识别完整影响范围，以及如何验证“旧状态已被清除”而非仅确认某条路径能运行。
- **已有验收：** V2 清单包含 5 个 F2P、190 个 P2P 选择器；实际 verifier 启动 Redis，再使用 Mocha 执行用户相关测试。
- **文档观察：** 需要能供审阅的状态规则、迁移范围和验证说明；小规模内部重构不强求另建架构文档。
- **接入风险：** 要支持 Node／Mocha 的原生验收，保证本地 Redis 就绪与数据隔离；核查邮件测试使用本地替身，不调用真实邮件服务。官方 V2 镜像声明为 Linux AMD64，在当前 ARM64 主机上须检查运行方式与性能。

### D. Navidrome：数据库备份恢复能力

- **身份与来源：** SWE-bench Pro V2，`instance_navidrome__navidrome-55730514ea59d5f1d0b8e3f8745569c29bdbf7b4`；[任务与原生 verifier](https://github.com/scaleapi/SWE-bench_Pro-os/tree/main/v2/tasks/instance_navidrome__navidrome-55730514ea59d5f1d0b8e3f8745569c29bdbf7b4)。
- **工作内容：** 增加备份配置和命令入口，从当前打开的 SQLite 连接创建备份、向当前连接恢复，并按文件名中的时间戳清理历史备份；还要处理内存数据库和保留数量为零的边界。
- **为什么适合：** 这是一个有明确交付结果的功能，需要协调配置、命令层、数据库生命周期和文件副作用。可以观察职责划分、错误处理、状态一致性及验证设计。
- **已有验收：** 官方 verifier 执行 `go test ./db`；F2P 名称是聚合套件 `TestDB`，不能解释成只有一个断言。读取到的补丁包含实际备份、修改数据库后恢复等场景。
- **额外资格条件：** 官方 P2P 清单为空，不等于“已证明没有回归”。预检前须检查 TestDB 的实际子场景，并另行确定原项目的回归与构建检查；原 benchmark 结果与补充回归分别报告。未补齐这项，不进入主效果对照。
- **接入风险：** Go／SQLite 依赖、AMD64 镜像运行、目录权限和时间相关行为；准备阶段必须满足离线执行所需依赖。所有数据库和备份仅在一次性任务工作区内。

## 2. 两个接续变体

它们复用 A／B 的目标和功能验收，属于我们的评测改编，不能冒充 benchmark 原生用例，也不能当作两个独立的新任务扩充样本量。先完成基础任务接入，再冻结变体的具体中间状态和提示词。

| 变体 | 输入状态与请求 | 要观察什么 |
| --- | --- | --- |
| B-R：设计后接续 | 保留当前代码、已有需求／设计／决策与进度文件；新会话根据文件继续 xarray 任务，不携带旧聊天 | 原有记录是否足以恢复目标和约定；是否重做已有决定或遗漏未完成事项 |
| A-R：部分迁移后接续 | 提供尚未完成的 smolagents 迁移工作区和公开开发测试产生的真实反馈；继续完成原目标 | 能否核对记录与代码状态、识别遗漏、处理反馈并更新文档 |

若研究“同一个中间状态下谁更会接手”，两组使用同一份冻结快照；若研究“自己留下的记录能否支持后续”，则接续各组自己的产物，并作为原试验的第二段分析。这两种设计不能混成同一个对照。不会把隐藏 verifier 细节或参考补丁作为接续输入。

## 4. 执行与分析建议

1. **先审阅 A／B，再预检。** 核对原始需求、参考行为、现有规范与测试覆盖；运行起始／参考实现，检查离线执行和结果稳定性。遇到语义冲突就暂停该题，不静默修改原题。
2. **首轮保持当前 skill 不变。** 同一 Agent、模型、任务、权限与预算比较 baseline／skill。预算根据任务和环境预检重新确定，不沿用小修复的 300 秒上限。先做少量配对检查流程，再决定重复次数。
3. **记录实际开发过程。** 查看需求是否落实、设计与实现是否一致、文档是否准确适量、失败结论是否有证据。不能仅凭 verifier 通过认定这些机制有效，也不把分析意见混入功能分数。
4. **分开检验 C／D 的适配与 skill。** 使用各任务自己的 verifier；Node／Go 不硬塞进 Python 测试入口。不能将环境失败归因于 skill。
5. **接续与真实协作另行推进。** A-R／B-R 检验文件接续。需要人类决策、需求变更和多 process 协调的能力，仍应在有真实决策点的开发任务中观察；这次没有编造 simulated user 或预设虚假批准。

共同任务输入只保留真实需求、项目规范、范围和授权，不逐步提示 Agent 应读哪份 skill、写哪些模板。A／B 原本就需要的用户文档照常保留；额外设计记录应服务于审阅和接续，不要求固定数量。
