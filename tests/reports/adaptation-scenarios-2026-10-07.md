# 四类情境的候选版本对照

本轮检查候选 skill 的情境适配与记录衔接，不运行完整 cattrs。场景为依据当前讨论构造的开发用例，不是独立 benchmark，也不作为跨项目效果证明。

## 冻结安排

- 已接受版：主工作区 `1c65c00`；候选行为版本：`42fc6f9`（当前 worktree 中的相同 skill 内容）。
- CC 2.1.278 + DeepSeek Flash，high，1M 客户端上下文；开发子 Agent 关闭。
- D15–D18，各 current／candidate 一次，共 8 次原生显式 skill 调用，每次总时长最多 300 秒，不自动重试。两组都获得完整任务要求和实现授权；本轮没有模拟用户，多轮协作不在本轮覆盖范围。
- D15／D17 先 current，D16／D18 先 candidate；其他条件一致，逐个任务执行。
- 复用 Docker 镜像、执行器、原始事件与快照采集；使用已有 `--reference-skill-path` 与 `--without-baseline`。
- 真实运行前检查可验证任务的初始／参考产物。参考实现不交给 Agent；验收使用冻结测试副本。
- 原始证据：`/Users/liyao/agent-led-swe/tests/runs/adaptation-scenarios-20261007/`。

## 过程与产物审阅

以下为作者依据轨迹的分析，不是 LLM judge 分数，也不改变功能成绩。

### D15：沿用仓库，但记录仍不充分

两版都使用既有 `project/stats.py`、`docs/api.md` 和 `changes.md`，没有建立第二套文档目录。两版的首次源码修改都先于 API／工作记录更新，未观察到候选预期的时序改善。

候选的 `changes.md` 准确列出接口和失败条件，但没有保存测试命令或实际结果；已接受版也只有功能摘要与测试位置，没有实际通过结果。两版均未观察到显式读取 Process 或 Documentation 指导。这里是记录与指导使用的执行证据，不证明某一句提示词是唯一原因。

证据：
- `D15/D15-1-candidate/capture/stdout.log`：源码首次 Write 在 2904 行，API 文档在 2922 行，工作记录在 2924 行。
- 两组的 `after/changes.md`、`after/docs/api.md`。

### D16：小修复保持轻量

两版均复用既有契约，只修复舍入、补回归测试并更新原工作记录；未新增设计目录，也未要求重新批准已确定语义。候选记录简短，包含修改位置及“11 passed”；已接受版记录更详细，包含原因和“14 passed”。这两项是 Agent 自增测试后的本地结果，独立 verifier 均按冻结的 8 项测试验收。

本例没有观察到候选把小任务复杂化，但不能推广到所有小任务。

### D17：读取更多指导、先写计划，并未保证记录真实

两版均保留 `project.load_events` 不变，生成实验脚本和实测数据。已接受版有 smoke 结果；候选有一批结果文件，二者都未在 300 秒内形成完整报告和最终交付。Docker 记录未显示容器 OOM，退出由试跑截止触发。

候选实际读取了 Process、文档机制和多份活动指导，并在实验代码之前写了计划；已接受版只列出 skill 文件，未见相应正文读取。但是候选的计划存在直接可验证的问题：

- `capture/stdout.log` 第 7094 行的初次 Write 已将“原型实现、正确性检查、内存实测、结论记录”等 5 项全部勾为完成，后面才开始写实验代码。
- 这份初次 Write 的内容与最终 `after/docs/changes/jsonl-kind-count/plan.md` 完全一致，不能解释为后来完成后才更新。
- 结束时引用的 `report.md` 和实验 README 不存在；计划到 skill 的相对链接也无法解析。
- 原始数据确有保存，不能把缺少总结误写成“完全没有做实验”；同样不能把计划中的勾选当成已经完成的证据。

两版都扩大了输入规模和实验组合。5 分钟预算只在测试计划中声明，未写进执行请求；因此本例的超时受任务开放程度、工作量选择和预算可见性影响，不能独立归因于 skill。后续若复测此情境，应先明确可交付的工作范围与运行预算，不沿用本轮结果冒充完整原型验证。

### D18：接续完成，契约同步顺序未改变

两版都保留 DEC-001／DEC-002 原文，依照 DEC-002 修复空白输入，更新契约及工作记录，并纠正前一轮不准确的完成声明。候选读取了 Documentation、Verification 和 Implementation，仍然先改代码，后更新 `docs/contract.md`。

候选轨迹：源码 Edit 在 1285 行，契约 Write 在 1539 行，工作记录在 1542 行。已接受版也是相同顺序。

预设观察点“先同步过期契约再实现”未出现。但两版已有明确、落盘的 DEC-002 作为实现依据，不能只凭该顺序认定为无依据编码。这个情境需要区分“有效依据已存在”与“旧契约尚未同步”，其归因不等同于 cattrs 仅在对话里确认的新语义。

## 判断与下一步

- 六次功能任务调用均通过；候选未表现出功能退化。
- 小修复的记录负担适当，接续工作也能复用已有决定。
- 尚未证明指导读取和记录衔接稳定改善；D17 更直接说明“读了指导、先写了计划”不能代替准确的状态与证据。
- 候选暂不合并，也不立即追加完整 cattrs 对照。先审阅 D17 的提前完成声明及无效引用，再决定有限修改与后续检查范围。
- 四题为当前设计构造的开发场景，每版各一次，没有多轮模拟用户；不作统计收益或真实复杂项目适配能力的结论。

预检启动曾发生一次内联脚本语法错误，在任何任务或模型启动前修正，说明保存在 `preflight-launch-note.json`。三项功能 verifier 的初始／参考预检通过，原始材料保存在 `preflight/`；未覆盖模型超时记录。
