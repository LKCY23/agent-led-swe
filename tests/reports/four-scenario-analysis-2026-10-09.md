# 四场景分析：设计落实、流程衔接与文档质量

结论：两版在这些任务中都能完成开发、验证和用户协作，但尚未稳定实现“依据及时保存、重要选择可把关、过程可接续”的完整设计。候选版有局部进步，也出现重复记录和多余确认，不能据此认定整体优于当前版。本轮只分析和提出建议，不修改 skill。

## 1. 分析依据与范围

以[评估设计规范](../evaluation-design.md)、两版冻结 skill、任务请求及用户授权为依据，从八组完整对话、工具调用与结果、每轮快照、最终文档及代码中核查相关行为。文档表达另对照通用文档撰写规范（`/Users/liyao/AILab/documentation-writing-standard.md`）。没有用文件数量、指导读取次数或功能成绩代替过程评价。

- [四场景结果](four-scenario-results-2026-10-08.md)：八组均通过独立功能验收并获用户接受；C 另有真实运行状态证据。各场景每版一次，没有无 skill 对照。
- 核对四份计划：current 的 29 份冻结文件在四场景完全一致；candidate 的 28 份文件也完全一致。原生调用均已验证，后文“未读取指导”仅指补充 references，不是 skill 未安装或入口未调用。
- 分析材料在 `/Users/liyao/agent-led-swe/tests/runs/four-scenario-analysis-20261009/`：各组 `*-tools.json` 保留工具输入、结果、回合和原始行号；`*-conversation.md` 保留完整问答；`*-docs.diff` 保存 A/B/D 文档变更。
- 另在只读挂载的 D 最终产物上核查文档示例和一个边界描述，保存脚本、参数与日志。它是分析用的补充核查，不修改原 verifier 成绩。

## 3. 是否遵循设计：关键在信息和时机

### 已落实的部分

各组均先调查实际仓库或环境，再实现和验证；成熟仓库沿用已有代码与文档位置，D 复用旧成果。A/B/C 在开发前有真实需求问答；B 能处理用户反馈；C 有真实服务调用与运行证据。不能将这些表现否定为“完全没用 skill”。

### 没有稳定落实的部分

候选版明确要求读取 Process、安排记录时读取文档机制，并在相关活动前读取指导。实际工具证据为：A/B 两版都未见补充指导读取；C current 读了 6 份活动/机制指导，candidate 读了 Process、3 份机制及 Verification；D current 未见读取，candidate 只读了 Verification 的前 80 行。候选修改没有稳定解决指导进入执行的问题。

读取本身不作为成败标准。更实质的缺口是：对应的工作安排、约定维护与决定历史也未稳定落实。A/B 的对话已经澄清了要求，但项目中的安排和已定依据没有同步形成；C candidate 虽然先写计划，计划依赖的“契约 → 基线 → 实现”安排却没有按确认后的内容及时维护。

**不能要求所有文档都先写。** 本轮应作如下区分：

| 信息 | 合理时机 | 本轮证据 |
| --- | --- | --- |
| 指导后续实现的约束、接口、关键取舍和工作安排 | 相关实现前明确；必要的新增约定保存或引用，已有充分依据直接复用。 | A/B 的对话澄清有效，但项目记录滞后；C 的 `.proto` 是有效事前契约，不能因为没有单独接口文档而忽略。 |
| 决定变化、计划和实际进展 | 影响后续工作时同步。 | C candidate 已按新协议写服务，计划却仍是旧草案，直到交付准备才重写。 |
| 实测结果、交付满足情况、可用功能说明 | 对应成果形成后记录；之后有变更再核对。 | A 的 quickstart、C 的验证记录在实现后形成是正常的；B 的旧计数残留才是问题。 |

## 4. 流程摩擦与归因

### 获取既定信息被变成了重新设计

A/B/C 的请求都说明用户持有确定接口或运行要求。各组仍先提出具体接口草案及多项默认选择，随后用户给出原规格并纠正。这些草案是提案，不能指责 Agent 已擅自实现了未经批准的方案；但先索取已有规格可以减少无效设计和用户审阅负担。

C candidate 的证据尤其直接：首次计划安排 `proto/kv/v1`、`src/kvservice`，首次回复提出 `Set/Get/Update`、50051 等草案；用户明确指出协议已经确定。随后 Agent 正确改用原规格。问题是信息获取顺序，不是不能修正反馈。

### 已授权选择又被写成等待批准

C candidate 的用户明确把缺键处理交由 Agent 判断。其决定日志 D-2 也准确记为 Agent 在授权内决定，但需求、契约和交付清单又写“需调用方确认”“在确认前未决”。这是已有授权未贯穿状态判断，不是缺少更多审批规则。证据：决定日志 D-2（`grpc-versions-20261008/candidate/after/docs/decisions/log.md:15`）、契约未决项（`grpc-versions-20261008/candidate/after/docs/design/contracts.md:66`）。

### 测试收尾也存在边界

模拟用户最后确认了 NOT_FOUND，但执行器收到 `accepted=true` 就结束，没有把该消息再交给开发 Agent。最终确认未回写不能全部归因于 skill。此前就存在的“已委托却列为未决”仍属于 Agent 的执行问题。证据：[接受后结束的代码](../collaboration_runtime.py)第 156–159 行与 C candidate 的最终用户回复。

### D 的任务解释并不完全相同

current 保留“缺失必需键仍返回部分映射”，candidate 将其也改为 None；模拟用户分别以“保持其他既有行为”和“缺失也属于失败”接受。这涉及本轮修复范围与原始完整规范之间的解释，7+69 项验收没有区分这一行为。两组多做或少做的工作不能全部算成 skill 的效果；应在下轮运行前明确范围，而不是事后挑选一种解释改分。

B current 的多轮修复、A 的转换边界调试、D 的回归检查均有实际技术问题支撑。本次没有证据证明它们仅由 skill 造成，也不能把它们自动算成流程摩擦。

## 5. 文档是否达标

总体是“能够帮助使用和维护，但准确性与状态一致性未稳定达标”。

### 有价值的表现

- A 直接扩展 quickstart/CHANGELOG，D 更新既有 `docs/partial.md`，符合仓库文档用途和语言，没有套入无关目录。
- B 一份开发记录容纳约定、机制、验证和未决项，便于审阅和接续；current 的实际变异检查有证据，不应因其他记录错误而否定。
- C current 的 README 与验证记录足以支持基本使用；candidate 保存了更完整的决定理由、版本摘要和验证条件。D candidate 运行了文档示例，发现旧示例后修正并复测，属于有用的闭环。

## 6. 对候选修改的判断

候选版在 C 更主动读取 Process/文档机制并建立早期计划，在 D 有实际文档示例核查；这是观察到的改善。A/B 的指导读取和事前项目记录却没有改善，C 又出现记录重复和授权状态混淆，D 的范围解释也不同。

因此，不能认定候选修改已经有效解决原问题，更不宜直接合并。可能的解释是关键执行要求分散在未读取的指导中，目录/模板示例又更容易被当作产物清单；这与 C 的轨迹相符，但单次对照不能确定因果。候选入口还移除了当前版“小型变更不需要完整文档目录”“模板不是必须逐一创建的清单”的直述，相关裁剪要求仍留在补充指导中。优化时应重新考虑这些关键信息的位置。主要时序、准确性和授权规则已经写明，不能把所有偏差都诊断成“规范缺失”。

## 7. 建议的优化顺序（待审阅，未实施）

| 优先事项 | 具体修改方向与文件 | 改后应观察到什么 |
| --- | --- | --- |
| 1. 让实现前的条件可执行 | 在 `SKILL.md` 的现有进入/推进规则中集中表达：进入相关实现前，缺失的已定依据与本轮安排已在项目中保存或引用；允许复用既有文件和代码契约。`process.md`、`design.md`、文档机制负责细化，去掉重复散落的表述。 | A/B 确认后及时保存必要依据；C 协议变更后先更新相关计划；D 直接复用充分依据，不重新建立全套设计。不是增加新的阶段或审批。 |
| 2. 分清获取信息与请求决定 | 调整入口、`requirements.md` 与人机协作机制：用户已持有的规格先索取；真正未定且未授权的取舍才提交备选与建议；已委托的选择记录决定和理由，不再列为等待批准。 | 不先展开另一套固定接口草案；C 的 NOT_FOUND 不在已自主决定后又成为阻塞项。主要是澄清已有规则的行动顺序。 |
| 3. 按用途选择记录的边界 | 文档机制把“已有载体能否承载、谁会使用、是否独立维护”的判断放在目录示例之前；示例只说明选择后的组织方式。统一契约在一处维护，其他材料摘要引用。 | 小任务可用简短合并记录；公共使用说明保持可读；拆出的每份材料有独立用途，不因读了模板而逐个生成。无统一文件数或字数限制。 |
| 4. 核查文档与实际证据 | 在 Verification / Delivery 现有检查中明确审阅受影响的文档差异：例子可运行、文字保留条件、结论对应实际版本与命令、状态与已授权决定一致；有变更时只复查受影响内容。 | B 的旧规则/计数和 C 的状态冲突被发现，D 不仅检查例子还核对正文边界。已有“准确、同步”要求转为具体检查，不再追加大量泛化提醒。 |

测试机制单独处理，不混入 skill 改动：

1. 让最后一条用户反馈交回开发 Agent，允许必要的状态同步和收尾后再封存产物；不规定必须写哪份文件，也不伪造用户回复。
2. 明确 D 中“缺失必需键”的保留/修复范围，解决本轮修复与原始规范的解释差异。新请求另存，旧轨迹和成绩不改。
3. 后续每次只验证一个明确假设，继续在 worktree 中对照。现有任务用于回归，另选未用于修改的新任务检查泛化；不因为结果不理想反复重跑直到通过。

先审阅以上改动方向，再形成最小 patch 和对应观察标准。本轮不新增流程层级，不发布新的 skill 版本。
