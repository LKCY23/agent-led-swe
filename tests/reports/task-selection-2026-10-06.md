# 主要评测任务：审阅建议

本轮旧候选建议已由[用户确认的四题组合](sample-suite-candidates-2026-10-06.md)替代。本文保留早期判断，不作为当前任务入口。

目标是观察需求、设计、实现、验证与可接续记录是否衔接。任务需要这些活动时才有分析价值，不能靠提示词强制生成一套文档。

## packaging：保留为实现完整性候选

冻结任务要求完成包元数据解析、字段与版本校验、RFC822 序列化及依赖解析；遮蔽涉及 metadata、requirements 和 parser 三个文件。接口和大量方法语义已经给定。

它适合观察多项要求是否落实、模块间行为是否一致、兼容性和交付说明是否可靠。但任务已替 Agent 做了较多接口设计，不能作为自主架构／接口设计的主要证据。旧的 300 秒预算也不应自动沿用：先审阅任务规模，再冻结新预算。

清理后的本地环境已通过重复预检，尚未在新网络环境启动效果对照。建议保留为次要用例，不把它等同于完整开发流程评测。

## DSPy：较接近模块改进，但仍需资格检查

冻结需求是给 ReAct 增加异步执行，并兼容同步和异步工具；保留推理循环、错误作为 observation、上下文截断重试、max_iters 和返回结果语义。参考变更跨 react.py 与 tool.py。

这里有真实的组件协作和兼容性取舍，适合观察设计说明、错误处理、需求覆盖和测试安排。公共方法方向已给定，规模仍有限，不能单凭它验证整体架构、多 process 或人类协作。

已有目标测试能区分起始与参考实现；回归却有两类独立阻碍：

1. 图片／PDF 等测试输入需要下载。应固定资源与来源哈希，检查本地供给方式能否保持原测试语义。
2. 模拟服务 10 秒启动检查与 asyncify 耗时断言有波动。应检查服务准备、资源争用和基线行为；不能靠加长原断言或删除测试获得通过。

建议优先审阅 DSPy 是否作为下一项候选；批准后先做环境资格处理，失败则换题，暂不接入正式执行入口。

## 仍缺少的覆盖

两项候选都不能充分验证从一般需求形成模块／接口设计，以及多轮需求变化和人类决策。后续仍需另选设计空间更大的真实功能任务；本轮没有未经审阅扩大任务集。

下一轮提示词只提供真实需求、仓库规范和必要约束，不逐步告诉 Agent 要读哪份 skill、写哪几个文件。功能由 verifier 验收；设计、记录、推进与交付由轨迹和实际产物分析。

本次仅依据本地冻结任务描述、补丁涉及文件和已有预检证据进行审阅，没有新增 benchmark 运行，也没有改动任务需求或测试。
