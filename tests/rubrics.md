## 1. 怎样使用这份 rubric

本文件细化 [测试机制](README.md)中的验收依据。评价对象是任务成果与实际开发行为，不是 Agent 是否复述了 skill 或使用了指定模板。

开发过程和决定权限由任务、项目约定及已有授权确定，rubric 不另设审批点或要求固定的设计深度。有无 skill 的对照使用共有的成果要求；是否读取指导、使用模板或遵循 skill 特有步骤，只作为 Skill 组的执行诊断，不直接作为两组成果比较的得分依据。

每个 case 运行前，从下列条目中选取适用内容，结合具体需求和项目约定写出可检查的条件。标明哪些是任务必须满足的要求，哪些仅用于质量观察；同一对照中的各组使用相同要求。不得根据运行结果临时增加必要项或放宽标准。

需要计划、设计和记录的任务，应向两组同样说明其用途和必要成果。例如“让维护者能审阅接口变化并继续开发”，不要求 baseline 使用本 skill 的文件名、模板或术语。信息可以保存在已有设计、issue 或工作记录中，按内容和用途判断。

不是所有任务都需要独立的模块设计或接口文档。仅改变内部实现且不影响契约时，接口设计项可以不适用；需要改变模块协作时，相关设计信息不能因没有要求某个文件名而省略。

下表用于追踪这些能力在 skill 中的依据；具体 case 的共有验收要求仍由任务约定确定。

| 评价条目 | 对应指导 |
| --- | --- |
| F1–F3：需求、兼容与验证 | [需求分析](../references/phases/requirements.md)、[验证指导](../references/phases/verification.md) |
| E1–E3：工程约定与设计质量 | [工程基线](../references/mechanisms/engineering-baseline.md)、[设计指导](../references/phases/design.md) |
| D1：工作安排与协调 | [Process](../references/process.md)、[Workflow](../references/workflow.md) |
| D2–D3：整体、模块与接口设计 | [设计指导](../references/phases/design.md)及其三类模板 |
| D4–D7：记录、表达与交付 | [文档机制](../references/mechanisms/documentation-and-traceability.md)、[交付指导](../references/phases/delivery-and-maintenance.md) |
| H1–H3：决定与人机衔接 | [人机协作](../references/mechanisms/human-collaboration.md)；H3 还需真实使用反馈 |

## 2. 判定方式

| 判定 | 使用条件 |
| --- | --- |
| **通过（pass）** | 证据支持该条目约定的要求已经满足。 |
| **不通过（fail）** | 有证据表明要求被违反或必要内容缺失，注明具体缺口。 |
| **无法判断（unknown）** | 缺少必要证据，或环境、采集、验收存在问题，暂时不能作出结论。 |

不适用的条目注明原因并排除，不计作通过。对“发生关键选择时才检查决策材料”等条件条目，提前定义适用条件，运行后根据实际情况判断是否适用。

部分满足但仍有已知必要缺口，按不通过记录并说明已完成部分。已确认遗漏必要记录是缺失；只有最终文件、没有形成时间的证据，则不能据此判断它是否在实现前起作用。

必要项不通过时，不宣称任务整体成功；必要项无法判断时，不宣称任务已通过。预先指定的严重违规，如越过明确授权或伪造验证结果，单独报告，不能由其他表现抵消。非必要的表达优化建议与必要项分别记录。

功能、工程质量、项目管理与文档、人机衔接、成本分别报告，暂不设总分和统一权重。官方 benchmark 验收与附加的项目开发要求分别列出。

## 3. 需求、功能与工程质量

| 条目 | 适用范围与通过依据 | 不通过或无法判断的典型情况 |
| --- | --- | --- |
| **F1 需求满足** | 对照约定需求，实际行为覆盖正常及相关边界场景；代码和测试能对应到所需能力。 | 只完成部分目标、漏掉已要求的错误路径；只有声称完成而无可核实依据。 |
| **F2 兼容与回归** | 变更涉及已有行为或使用方时，相关兼容承诺与回归检查成立。 | 提供方测试通过但调用方失败；已要求的兼容路径被破坏或没有验证证据。 |
| **F3 验证可信** | 检查确实执行，版本、输入与结论相符，验证内容能观察目标行为。 | 将计划执行写成已通过、检查了旧版本，或只验证了替代品却声称真实集成成功。 |
| **E1 工程约定** | 实现遵守适用的仓库规范、依赖方向、接口及已确认设计；例外有依据。 | 为通过测试绕过既定模块边界、引入违反约定的依赖，或擅自改变公共行为。 |
| **E2 职责与协作** | 新增或修改的职责归属明确，复用已有能力，接口与使用方行为一致。 | 同一规则在多处冲突实现、调用方依赖未约定的内部细节，或必须靠隐含假设才能组合。 |
| **E3 理解与修改** | 审阅者能根据代码和必要说明定位行为、依赖及修改影响；复杂性有当前需求依据。 | 为无关需求增加抽象、分散一次变更的逻辑，或留下缺乏依据的特殊分支。 |

E2、E3 的问题必须指向具体行为或修改影响，不能仅凭个人喜欢另一种架构、文件数量或代码行数判定失败。静态审阅只能支持可理解性与修改影响的判断；“维护更容易”的结论还需要后续修改或实际使用证据。

## 4. 项目管理与文档

### 4.1 按产物用途检查

| 条目 | 何时适用 | 通过依据 | 问题表现 |
| --- | --- | --- | --- |
| **D1 需求、计划与协调** | 需求需要澄清、拆解或协调时。 | 区分目标、已有依据和未决问题；工作对应产出、依赖及完成检查。多个 process 共同交付时，明确各自贡献、共享约定和整体检查。 | 只有通用步骤；缺失关键工作；未决选择被写成既定方案；局部通过被当作整体完成。 |
| **D2 整体与模块设计** | 系统结构、主要交互、模块职责或机制发生实质变化时。 | 在受影响的范围说明职责与交互，补齐当前实现所需的关键机制；重要取舍和未决事项可见，未受影响的设计可引用。 | 仅列目录和类名；影响当前实现的关键机制缺失；设计与代码存在未解释的偏离。 |
| **D3 接口文档** | 新增或改变对外能力、数据契约或使用方约定时。 | 使用方能理解输入输出含义、约束、错误与副作用，并据此正确使用和验证接口；对本任务重要的单位、顺序等语义已明确。 | 只有类型签名，缺少必要语义；提供方与使用方依据不同约定；维护多份相互冲突的定义。 |
| **D4 进展、变化与决定** | 工作分步推进、存在待决事项或约定变化时。 | 记录与产物一致，能区分提议、决定、实现和验证；变化关联受影响工作及依据。 | 计划长期停留在初始状态；提议冒充批准；记录称已验证但没有对应结果。 |
| **D5 交付与接续** | 交付成果或结束当前请求时。 | 能查清交付范围、完成情况、证据、限制和下一步；必要使用与维护信息可用。 | 当前计划完成被写成整个功能完成；隐藏未完成项；后续开发者无法判断该从哪里继续。 |

文档可以合并或分开，结构只要服务上述用途即可。不要求每个模块都写完整设计，也不要求把接口契约已经表达的内容复制进模块文档。

### 4.2 检查表达质量与实际作用

**D6 表达质量。** 内容准确、术语一致，事实、提案、决定和结果可区分。每段应提供所需信息、解释依据或帮助读者行动。示例、图表及边界说明有实际用途时可以保留。

指出重复时，需要说明重复了什么、是否增加新的含义，以及如何妨碍查找、判断或维护。例如，在计划的每一节重复“本轮不实现”没有提供新的安排；在目标处说明范围、在进展处说明尚未完成的具体工作，则承担不同用途。表达问题是否使该项不通过，按 case 预先确定的文档用途判断，不设置通用字数上限。

**D7 形成与更新。** 当任务需要设计把关或持续记录时，检查文档是否在相关实现前提供了依据、是否随变化更新。使用文件快照和实际操作顺序，不依赖 Agent 自报。

- 若只需最终成果说明，事后整理不自动构成问题。
- 若明确要求实现前提供设计，而证据显示先实现后补写，则该要求不通过。
- 若缺少时间顺序证据，只能评价最终内容；不能认定文档曾指导开发。

## 5. 人机衔接

| 条目 | 通过依据 | 问题表现或证据限制 |
| --- | --- | --- |
| **H1 决策归属** | 在既有目标、偏好与授权内自主推进；超出约定的重要选择被明确提出。 | 将未定的用户偏好直接当作决定；对已有明确约定反复请求笼统确认。 |
| **H2 决策材料** | 需要人类决定时，材料说明具体问题、可核实证据、建议与影响，使人类能判断取舍。 | 仅问“是否继续”，隐藏改变了承诺的后果，或要求人类重新完成技术调查。 |
| **H3 实际协作作用** | 真实使用中，人类能依据材料作决定或接续工作，且能指出帮助及对应证据。 | 需要大量补问才能理解状态，或信息负担超过帮助；没有实际人类反馈时不推断协作体验。 |

H1、H2 可通过受控场景与实际产物检查，H3 主要来自实际使用评估。没有发生需要人类决定的问题时，不因没有提问扣分；问题多也不意味着协作好。人类尚未决定时的合理等待，不等同于实现失败。

当前不引入 simulated user。真实人类干预应记录内容与影响；两组干预条件不一致时，协作观察单独报告，不直接归因于 skill。

## 6. 效率与负担

记录运行时间、可获取的 tokens 和费用；必要人工投入有实际测量时记录时间，否则保留具体观察，不估造数字。缺失数据记为未知。

配对比较同时看是否完成相同要求，以及完成的质量。区分新增的有效调查、设计和验证成本，与重复读取、重复确认、重复文档或无关改动造成的成本。不能仅因某组写得少或更早停止，就认定更高效。

报告全部尝试的开销，并在质量与成果可比的运行之间比较效率。除非任务已有预算要求，不事后设置“多用多少 tokens 即失败”的阈值。

## 7. 判定示例

以下用于解释标准，不是已选 benchmark case，也不代表已经执行的测试。

| 观察到的情况 | 应如何判断 |
| --- | --- |
| 模块只有几行修复，现有契约仍适用；提交说明和验证记录足以解释改动。 | 不因缺少独立模块设计文件判失败，按本任务实际需要检查。 |
| 接口返回耗时数值，类型完整但没有约定单位；两个使用方作出不同解释。 | D3 有具体语义缺口，不能以文档存在或类型检查通过判定满足。 |
| 计划写明某项工作依赖已确认契约，指出本地验证和真实集成各需什么产出。 | D1 有可推进的依据，不要求再按六项活动补齐形式上的章节。 |
| 最终设计与代码一致，但没有记录能说明设计何时形成。 | 可以检查 D2 内容；D7 的事前作用无法判断。 |
| 用例只要求写计划，Agent 说明计划已交付、功能尚未实现，并保留未决事项。 | 按计划任务验收；不能据此宣称整个功能开发 process 已完成。 |
| 功能检查通过，但计划多次复制同一授权声明。 | 功能结果照实记录；D6 单独判断重复及其对用途的影响。 |
| 有记录明确表明未执行集成检查，交付却声称整体已验证。 | F3、D4/D5 存在与证据冲突的结论；不能以其他检查通过抵消。 |

## 8. 评审输出与首次校准

每项结论至少说明：适用要求、判定、证据位置，以及影响或无法判断的原因。配对比较先分别判定各组，再解释改善、退化和成本；不以参考补丁的写法作为唯一正确实现。

首次应用前，用少量产物校准“信息充分”“表达重复”“需要人类决定”等定性判断，优先审阅有分歧的条目。校准完成后固定该轮标准；确需修改评价依据时记录原因，对受影响的两组使用一致标准重新评价，保留原结果。

人类校准的重点是判据能否反映已有约定、文档是否支持开发与审阅，以及是否遵守已确定的人机分工；不在评分过程中重新规定设计深度或决定权限。条目不会自动全部成为每个 case 的硬性要求；是否必要及具体证据在 case 定义时确定。
