# Process｜单项需求的开发组织

围绕一项需求或变更目标，结合软件现状与 lifecycle 组织开发工作。本文负责需求归组、工作安排、调整与完成判断；具体活动要求由各活动指导说明。

## Identify the work

收到新需求或对已有工作的补充时，先对照现有目标、约定和实际成果，确定本次输入属于哪项工作。

| 输入情况 | 处理方式 |
| --- | --- |
| 澄清、约束或修复，服务于尚未完成的原目标 | 继续原 process，更新受影响的要求和安排。 |
| 原目标或验收条件发生变化 | 明确改变了什么及其影响，按人机协作机制形成决定后更新约定。 |
| 引入可独立理解、推进和验收的新目标 | 组织新的 process，关联相关工作。 |
| 已交付成果的独立改进或修复 | 组织后续 process，关联原交付和问题证据。 |

需要共同设计和验收的要求归入同一 process；可独立形成结果的目标可以拆分。涉及多个模块本身不构成拆分理由。多个 process 存在依赖或共同交付要求时，使用 [Workflow 指导](workflow.md)。

明确 process 的预期结果与范围，并区分本次请求要推进的部分。例如，功能开发中的一次设计讨论，不会自动把整个 process 的目标改成“交付设计”。如果目标本来就是完成设计，则以设计成果验收。

## Organize the work

**形成或调整计划时，依次检查已有依据、工作缺口和后续影响。**

1. **检查已有依据。** 阅读相关需求、设计、工程约定、代码和证据，核对其适用范围、实际状态及对本次工作的覆盖。充分且仍有效的成果直接引用，只补充缺口；已有文件的名称或数量不能证明依据充分。工程约定不足时，按 [工程基线机制](mechanisms/engineering-baseline.md)补齐当前设计或实现需要的约定。
2. **根据缺口选择活动。** 用下表定位需要开展的工作；同一需求可以需要多项活动，也可以复用已有产出。

| 当前缺口或工作需要 | 读取并使用 | 要形成的结果 |
| --- | --- | --- |
| 问题、预期结果或范围不清 | [Problem Framing](phases/problem-framing.md) | 可用于定义需求的问题与目标说明。 |
| 行为、约束或验收条件未明确 | [Requirements Analysis](phases/requirements.md) | 可以据此设计和验收的需求约定。 |
| 职责、接口或关键机制尚不足以指导实现 | [Design](phases/design.md) | 当前变更所需的整体、模块或接口设计，以及未决事项。 |
| 实现依据已具备，需要构建或接入能力 | [Implementation and Integration](phases/implementation.md) | 对应约定的实现与集成产物。 |
| 需要检查实现、需求覆盖或工程约定 | [Verification and Validation](phases/verification.md) | 可支持完成判断的检查结果与证据。 |
| 准备交付，或处理已交付成果的后续需求 | [Delivery and Maintenance](phases/delivery-and-maintenance.md) | 交付结论、必要的使用维护材料，或后续工作的依据。 |

3. **确定工作深度与后续影响。** 根据变更涉及的行为、使用方、兼容承诺及不确定性，决定设计和验证需要细化到什么程度：

| 当前情况 | 所需工作深度 |
| --- | --- |
| 已知原因的局部修复，既有设计仍适用 | 明确修改依据、影响范围和回归检查，复用已有设计。 |
| 新增或变更公共接口、关键机制 | 细化契约、内部机制及相关使用方的影响，安排必要的兼容、迁移和集成验证。 |
| 可行性或设计事实尚不确定 | 先安排调查或试验，明确假设、判断依据和结论；区分探索结果与已确定方案。 |

将目标所需的文档更新、使用维护准备纳入工作安排。探索成果转为交付实现时，重新核对相应设计、验证和维护依据；当前尚不需要解决的细节留待涉及它们时细化。

在项目的任务或变更记录中说明选定工作的产出、依赖、完成检查与维护位置，按依赖安排顺序。简短工作可用段落表达，需要展开时参考 [Process 计划模板](../assets/templates/process-plan.md)。记录的复用、合并和更新遵循 [文档机制](mechanisms/documentation-and-traceability.md)。

## Advance and revise the plan

**开展一项工作前，核对其所需产出是否已具备，并读取对应活动指导。** 准备实现时，按 Design 指导检查当前变更的设计依据，同时核对工程基线与交付条件。某个依赖未满足时，先处理该缺口，继续推进不依赖它的工作。

完成一项工作后，对照计划中的完成检查核对实际产出，记录结果或证据链接，再判断依赖它的工作能否继续。记录“设计已确定”“代码已实现”“检查已通过”时，分别给出对应依据。

| 执行中的反馈 | 返回与调整 |
| --- | --- |
| 实现违反已确定的需求或契约 | 返回相关实现，修复并重新验证受影响的行为。 |
| 新证据使设计假设或机制失效 | 返回设计；补充所需调查，重新判断受影响工作的深度与依赖。 |
| 需求、范围或验收条件需要改变 | 返回需求与决策，明确变化及影响后重新核对活动范围与交付安排。 |
| 所需产出不可用，或发生共享契约变化 | 重新安排依赖工作；涉及其他 process 时使用 [Workflow 变更指导](workflow.md#handle-changes)。 |

在约定范围内可以通过调查或实现解决的问题由 Agent 推进；涉及人类意图、偏好或重要承诺的选择，按 [人机协作机制](mechanisms/human-collaboration.md)准备问题、证据、建议和影响，等待相关决定后继续依赖它的工作。

按 [文档机制](mechanisms/documentation-and-traceability.md)同步受影响的约定、计划和进展。保留仍然有效的成果与证据，不因局部变化重新开展全部工作。

## Establish process completion

准备报告完成时，将实际成果与 process 的约定目标、交付清单及验证记录逐项对应，按 [交付指导](phases/delivery-and-maintenance.md)形成结论。仍有未满足或未验证的承诺时，明确它们及其影响；需要接受重要限制时，使用人机协作机制。

当前请求完成不等于整个 process 完成。只完成设计讨论时，记录设计结果和剩余开发工作；目标本身是交付设计时，按设计的验收条件判断完成。参与 workflow 的 process 即使局部完成，也仍需由 workflow 检查整体结果。

若此前完成判断有误，追加更正并处理原有承诺，不能将遗漏包装成新需求。交付后的独立改进或修复，按本文的工作归属规则组织后续 process。
