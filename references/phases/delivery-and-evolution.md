# Delivery and evolution

Compare actual artifacts with the agreed delivery checklist. Report each material commitment as met, partial, unmet, or unverified with evidence. Explain deviations, known issues and remaining work. Delivery of a code change does not establish deployment or operational acceptance unless those were included and verified.

Provide the information needed to use or maintain this result: relevant entrypoints, configuration, public behavior, usage, verification, and troubleshooting as appropriate. Update the project's established docs rather than creating every possible manual. Link detailed evidence instead of pasting logs into summaries.

Use [human collaboration](../mechanisms/human-collaboration.md) when acceptance involves human preference or a consequential remaining limitation. A human accepting a limitation does not turn an unrun test into a pass; record both accurately. Existing authorization covers ordinary completion within scope without a further generic approval.

Keep current design and baseline aligned with accepted changes. Append decision-to-implementation links when known, and finish the work record with the checked revision, delivered artifacts and open follow-up. A handoff index should make the next meaningful action apparent.

For maintenance, recover the existing contract before changing behavior. Diagnose against it, record relevant defect evidence, and verify the repair. Revisit requirements/design when feedback genuinely changes the intended solution. Reuse this workflow at the affected scope instead of reopening the whole project.

Publishing, installing, deploying, creating external tickets, or changing other environments must follow the user's actual authorization and the existing project workflow. The skill does not grant those actions by itself.
